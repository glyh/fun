# Design: Type-Aware Macro Interleaving Handshake

> **Status:** Design-only. No implementation source changes.
>
> **Parent:** [TYPE_AWARE_INTERLEAVING.md](plan-for-macros/TYPE_AWARE_INTERLEAVING.md) —
> the motivation and required compiler shape. This document encodes the resolved
> decisions from the Wayfinder `Type-aware macro interleaving handshake` ticket.

---

## 1. Architecture

### 1.1 No OCaml 5 effects

The driver uses an **explicit, first-order state machine** (a queue loop) rather
than OCaml 5 effect handlers. This keeps the semantics directly portable to C#.

### 1.2 Owner: semantic module driver

A new module — `macro_driver.ml` / `driver.ml` — lives near the `elab_driver` /
`Core_loader` boundary. It is called after parsing/enforesting and before (or
interleaved with) elaboration of runtime code.

**Not in:**
- `Elab_infer` — driver is a separate concern from type inference.
- `Expand` directly — driver calls into expand/elaborate as services, not the
  reverse.

### 1.3 Deterministic ordered pass

No suspension/defer queue. The driver processes one top-level declaration at a
time in source order, with a finite set of semantic operations between each
declaration. Every pass is deterministic.

---

## 2. Pipeline Split

### 2.1 Parser / enforester: unresolved syntax only

```
source → Raw_syntax → Enforest → Syntax.t (unresolved annotations)
```

The parser and enforester produce `Syntax.t` with **unresolved** macro
annotations. No semantic name resolution, no `known_type_names`, no
`MacroBinding` compilation happens during parsing.

### 2.2 Split annotation types

| Before (current)                  | After (design)                          |
|-----------------------------------|-----------------------------------------|
| `MacroAnnotation` carries arity   | `MacroAnnotation.t` — unresolved syntax |
| One type conflates both phases    | `MacroKind.t` — resolved semantic kind  |

- **`MacroAnnotation.t`** lives in `Syntax.t` only.
- **`MacroKind.t`** is a resolved sum type used in compiled macro exports and
  the driver's internal state.

### 2.3 MacroKind sum type

```ocaml
type resolved_type_ref = ... (* semantic type reference *)

type macro_kind =
  | ExprAny                         (* : Expr — any expression *)
  | ExprBinder of string            (* : Expr(A) where A is not a known type *)
  | ExprConstraint of resolved_type_ref  (* : Expr(Foo) where Foo resolves to a type *)
```

No invalid option-pair states. The sum type guarantees exactly one interpretation.

### 2.4 Final output is macro-free

Macro definitions and macro call sites are compile-time artifacts consumed
entirely by the driver. The final semantic / runtime module output contains no
`MacroBinding` nodes and no macro-annotation syntax.

---

## 3. Annotation Resolution Rules

### 3.1 Type namespace only

`Expr(Foo)` resolves as `ExprConstraint` **only** if `Foo` is a type in the
current *prior* type namespace (types declared in earlier binding groups).
Values, constructors, macros, pattern synonyms, and later declarations in the
same module do not count.

### 3.2 Unresolved uppercase names are binders

If `Foo` is not a known type, the annotation remains `ExprBinder`. Typo
detection (e.g. `Expr(Intt)` when `Int` exists) is deferred to a future
warning/lint pass — the driver does not guess.

### 3.3 Resolved constraints use semantic type refs

`ExprConstraint` carries a semantic `resolved_type_ref`, not a bare string.
This avoids string-equality bugs across module aliases, imports, and re-exports.

---

## 4. Semantic Driver Queue

### 4.1 Input and output

```
Input:  Syntax.module_   (unresolved annotations, ordered top-level bindings)
Output: Core.module_artifacts × SemanticExports.t × MacroExports.t
```

`Surface.t` is a per-binding lowered intermediate produced inside the driver
and optionally preserved for debug/test traces — it is not the authoritative
final module artifact.

### 4.2 Pseudo-code queue loop

```ocaml
let run_driver (m : Syntax.module_) : module_output =
  let ctx = init_semantic_ctx () in
  let macro_registry = MacroRegistry.empty () in
  let queue : Syntax.struct_binding Queue.t = Queue.of_list m.bindings in
  let runtime_bindings = ref [] in
  let macro_exports = ref [] in
  let fuel = initial_fuel in

  while not (Queue.is_empty queue) do
    let binding = Queue.pop queue in
    match binding with

    (* Import *)
    | Syntax.Import { module_path; ... } ->
      let module_result = MacroLoader.load macro_registry module_path in
      ctx <- extend_ctx_with_type_exports ctx module_result.semantic_exports;
      macro_registry <- MacroRegistry.import macro_registry module_result.macro_exports;
      runtime_bindings := record_runtime_dependency module_path :: !runtime_bindings

    (* Macro definition *)
    | Syntax.MacroBinding ({ annotations; body; ... } as mb) ->
      let kind = MacroResolver.resolve_kind ctx annotations in
      let fuel = decr_fuel fuel in
      let compiled =
        MacroCompiler.compile ~fuel ~ctx ~kind ~hygiene:capture_hygiene mb
      in
      macro_registry <- MacroRegistry.register macro_registry compiled;
      macro_exports := compiled.export :: !macro_exports

    (* Runtime declaration *)
    | Syntax.ValueBinding _ | Syntax.TypeBinding _ | Syntax.ModuleBinding _ ->
      let elaborated = Elaborate.elaborate_declaration ctx binding in
      runtime_bindings := elaborated :: !runtime_bindings;
      ctx <- extend_ctx_with_binding ctx binding

    (* Macro-generated declarations (re-enter queue) *)
    | Syntax.MacroCallBinding { call; hygiene } ->
      let generated = MacroExpander.expand_call ~ctx call in
      let annotated = attach_hygiene hygiene generated in
      Queue.prepend_all_preserving_order queue annotated
  done;

  { runtime = List.rev !runtime_bindings; macros = List.rev !macro_exports }
```

### 4.3 Top-level only for now

The driver processes top-level module bindings only. Nested/local macro
definitions are rejected with a clear error:

> "Nested macro definitions are not yet supported. Move this macro to the top
> level of the module."

A nested driver can be added later without changing the top-level design.

### 4.4 Macro-generated declarations re-enter the queue

When a macro call produces declarations (`MacroCallBinding`), those declarations
are spliced onto the front of the remaining queue immediately after the current
item. They are processed in order, preserving the internal atomicity of each
top-level binding group.

Hygiene metadata (defining scope + call site) is attached to generated
declarations so the elaborator can produce correct spans and avoid capture.

### 4.5 Transactional / fail-stop

Each driver step is atomic with respect to the semantic context. If any step
fails (compilation error, elaboration error), the driver stops and reports that
first error. No best-effort recovery in the minimal design.

## 5. Macro Imports

### 5.1 Unified import path

Imported macros are loaded through the same driver pipeline as local macros.
They are represented as `Import` steps in the queue that extend the semantic
type namespace and macro registry for subsequent bindings.

### 5.2 Reject `visit_macros` separate path

The current `Core_loader.visit_macros` path that compiles imported macros
separately is replaced. Existing test/load helpers that use it may remain as
wrappers that call the canonical driver, but the independent compilation path
is removed.

---

## 6. Macro Exports

### 6.1 First-class output

`MacroExports.t` is an explicit, first-class output of the driver alongside
`Core.module_artifacts` and ordinary semantic/type exports. It contains closed,
compiled macro artifacts:

```ocaml
type macro_export = {
  name : string;
  kind : MacroKind.t;                       (* resolved annotation kind *)
  compiled : MacroCompiler.compiled_macro;   (* closed compiled artifact *)
  capture_env : semantic_env_fingerprint;    (* prior semantic context fingerprint *)
  hygiene : hygiene_metadata;
  module_id : module_identity;
}
```

### 6.2 Consumption by importers

When a module is imported, the imported module's ordinary semantic/type exports
extend the type namespace, and its `macro_exports` extend the macro registry.
The importing driver validates ABI compatibility using the module identity and
semantic context fingerprint.

---

## 7. Recursive Macros

### 7.1 Self-recursion

Self-recursive macro definitions are allowed with an explicit provisional
cell/placeholder:

1. Before compiling the macro body, register a provisional entry in the macro
   registry.
2. Compile the body against the context that includes the provisional entry.
3. On success, replace the provisional entry with the compiled artifact.
4. On failure, roll back (remove the provisional entry) and report the error.

### 7.2 No mutual recursion

Mutually recursive macro groups are not supported in the initial design. An
attempt to define two macros that refer to each other's compilation results
before both are registered produces an error.

### 7.3 Expansion fuel / stack guard

Every macro expansion consumes one unit of fuel. The driver has a configurable
fuel limit (e.g. 256) per module. Exceeding the limit halts with a "macro
expansion exceeded fuel limit" error. This guards recursive macros against
non-termination.

---

## 8. One Canonical Registration Path

There is exactly one semantic macro-registration path: the driver's
`MacroRegistry.register`. All other paths (parse-time registration, test helper
registration, `visit_macros`) are either retired or re-implemented as thin
wrappers that delegate to the driver.

---

## 9. Cache Identity

Cache validity for compiled macros is based on **resolved macro exports**, not
raw syntax alone:

- Module identity / source digest
- Macro name
- Resolved `MacroKind`
- Prior semantic environment fingerprint (type namespace, imported module
  versions)
- Macro ABI version

The important invariant is that raw syntax/source text is not sufficient to
reuse a compiled macro. A cache hit must match the resolved export identity,
including the resolved kind and the semantic environment fingerprint.

---

## 10. Call-Time Expansion

Call-time (use-site) macro expansion remains syntactic. The type-awareness in
this design is limited to **annotation resolution at definition/export time**.

When a macro is called, the expander receives the already-compiled macro
artifact (with its resolved `MacroKind`) and expands syntactically. No semantic
query happens at the call site.

---

## 11. Diagnostics

Minimal diagnostics only:

- Annotation resolution results are recorded in a per-module diagnostic log.
- Unresolved uppercase-name annotations produce a note-level diagnostic
  during the driver pass (not an error).
- Errors (incompatible macro kind, phase-invariant violations, fuel exhaustion)
  produce structured error values, not exceptions.

Stage 12 expansion UX (rich diagnostics, source-span annotation of expansion
steps, interactive debug) is deferred to a separate ticket.

---

## 12. Staged Migration

The migration is staged, with each step delivering a canonical end-state
before the next begins:

| Stage | What | Canonical end-state |
|-------|------|---------------------|
| 1 | Split `MacroAnnotation.t` / `MacroKind.t` AST types | Unresolved annotations in syntax, resolved kinds in driver |
| 2 | Remove `known_type_names`, add unresolved annotation pass-through | Parser/enforester produces no semantic macro decisions |
| 3 | Implement semantic module driver skeleton with queue loop | Driver exists and is callable, no behavior change yet |
| 4 | Implement `MacroResolver.resolve_kind` against semantic context | Annotations resolved at definition time |
| 5 | Canonical macro registration in driver; wrap old paths | One registration path |
| 6 | Macro-generated declaration re-entry into queue | Generated code processed inline |
| 7 | Self-recursive cells + fuel guards | Recursive macros with safety |
| 8 | Replace `visit_macros` with driver-based import loading | Unified import path |
| 9 | Retire old paths; remove dead code | Clean module boundary |

## 13. Acceptance Tests

The following must pass before this ticket is considered complete:

### Core behavior
- Prior type constrains annotation: `: Expr(MyType)` resolves as constraint
  when `MyType` is a type declared above.
- Later type does not constrain: `: Expr(LaterType)` remains binder when
  `LaterType` is declared below.
- Existing binders still work: `: Expr(SomeUnresolvedName)` produces
  `ExprBinder "SomeUnresolvedName"` and preserves the existing implicit binder
  behavior.
- Imported macro matches local: `: Expr(ImportedType)` resolves as constraint
  when the type comes from an import.

### Queue / ordering
- Macro-generated type affects following binding: a macro that emits a type
  definition makes that type visible to subsequent declarations.
- Generated batch is ordered: multiple declarations from one macro call are
  processed in source order within the queue.

### Clean output
- Macro definitions absent from runtime output: `MacroBinding` nodes do not
  appear in `Core.module_artifacts`.
- Macro calls absent from runtime output: expanded code replaces call sites
  before elaboration.

### Annotation safety
- Unresolved annotation cannot escape: `MacroAnnotation.t` never appears in
  driver output or exports.
- Diagnostic explains binder vs constraint: when `: Expr(Foo)` resolves as
  binder, a diagnostic note records `Foo` as an unresolved name.
- Misspelled annotation remains binder: `: Expr(Intt)` (when `Int` exists)
  becomes a binder; a future-warning hook is present but not enabled.

### Imports
- Import steps extend type namespace for subsequent bindings.
- Imported `macro_exports` are validated against ABI version and context
  fingerprint.

### Cache
- Cache invalidates on resolved annotation change: changing a type alias
  invalidates cached macro exports that depend on it.
- Cache keys on resolved context fingerprint, not raw syntax.

### Generated code
- Generated spans trace to macro call/template: spans on generated declarations
  carry both the defining-scope span and the call-site span.

### Post-driver invariant
- `MacroBinding` cannot appear after the driver has processed a module.
